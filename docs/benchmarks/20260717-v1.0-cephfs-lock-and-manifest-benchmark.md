# CephFS lock and aggregate manifest benchmark

Version: v1.1
Date: 2026-08-10
Status: current baseline and v2 candidate

## Environment and scope

- Host: `node4`
- Storage: the production CephFS bioinformatics resource tree
- Binary: locally built Linux `biofetch`
- Workload: read-only validation; logs and aggregate output under `/tmp`

This baseline records storage behavior, not a universal performance target.
Concurrent CephFS load can materially change elapsed time.

## STRING network snapshot lock

Input snapshot:

```text
/cephfs_data/genostack_v3/genostack_php/public_file_data/database/bioinfo/resources/string/v12.0
```

This observed snapshot predates the normalized `string/network/<version>`
layout. Its path is benchmark evidence, not a current layout example.

Command:

```bash
/usr/bin/time -v biofetch string network lock \
  <snapshot> \
  --workers 4 \
  --dry-run \
  --log-dir /tmp/biofetch-string-lock-benchmark
```

Observed scale and result:

- files hashed: 37,605
- snapshot bytes: 142,879,135,466 bytes (about 133.1 GiB)
- elapsed time: 22 minutes 27.49 seconds
- peak resident memory: 92,720 KiB
- result: success; no snapshot manifest was modified

Interpretation: memory and scheduling remain bounded, while elapsed time is
dominated by full CephFS reads. Four workers are the conservative default;
higher values require measurement because shared-storage contention can reduce
throughput.

## Aggregate manifest

The aggregate builder was run against the full resource tree with output under
`/tmp`.

Observed model:

- databases: 9
- snapshots: 19
- child file records: 137,614
- child bytes: 267,217,086,426
- repeated `manifest.toml` SHA256:
  `cf7432156891e61b92f9c723d4b3b8d0cb32ae8ef214925bb855297967c826af`

The identical digest across repeated builds confirms deterministic output at a
fixed input tree and output location. Aggregate generation hashes child lock
files but does not rehash the large files referenced by those locks.

## Aggregate manifest v2 fast path (2026-08-10)

The aggregate v2 implementation was validated against the current resource
tree with the output written only below `/tmp`. The snapshot-aware inventory
digest was identical before and after each run:

```text
locks: 30
inventory digest: 451887a18d7340ad5448e1cf034d92fdc30c3eabbe139c1efa6ebac61da1b04e
databases: 16
snapshots: 30
child file records: 141779
child bytes: 284095047132
```

The v2 binary was built from the implementation worktree and invoked as:

```bash
/tmp/biofetch manifest build \
  /cephfs_data/genostack_v3/genostack_php/public_file_data/database/bioinfo/resources \
  --output /tmp/<run> --formats toml,json,tsv --workers <n>
```

Observed runs on `node4` were:

| workers | elapsed | user | sys | peak RSS | result |
| ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 8.99 s | 1.43 s | 0.12 s | 76,564 KiB | success |
| 4 | 0.61 s | 1.44 s | 0.19 s | 103,504 KiB | success |
| 4 (repeat) | 0.61 s | 1.52 s | 0.20 s | 102,736 KiB | success |
| 8 | 0.52 s | 1.37 s | 0.18 s | 112,208 KiB | success |

All three formats had the same SHA256 at workers 1, 4, and 8:

```text
manifest.toml  b14bb6b94db718731f55b57eef8a76a2e18722bd5bea7e4d76ac8e374560f0b2
manifest.json  32a3d8360a3232e268b05a90abfd32ae57ef5a8cd3e0d620a34682fac0f7efe3
manifest.tsv   e10bb8fd497638ea0f6a4b4ca840c69c802eb05f33e73e8eb23c5755644635d6
```

The previous v1 run recorded in the implementation plan reached the 180 s
timeout without completing (`elapsed=180.18`, `user=2.63`, `sys=2.93`). A
fresh reference run with `dist/biofetch` reached the planned 300 s timeout
without producing an aggregate (`elapsed=300.01`, `user=6.26`, `sys=7.87`,
peak RSS 31,700 KiB, exit 124). The new v2 fast path therefore completes at
least 20 times faster than the earlier lower-bound timeout and over 490 times
faster than the fresh 300 s lower bound at four workers, while preserving the
full current inventory.
The output is a candidate only; the published v1 aggregate remains unchanged
until consumer compatibility and separate publication authorization are
complete.
