# HMDB browser acquisition and lock implementation plan

Version: v1.0
Date: 2026-07-27
Status: planned

## Goal

Make the HMDB command family honest and usable when the official download
endpoint requires an interactive browser authorization or Cloudflare
challenge:

1. keep direct `fetch` available for an official machine-accessible endpoint;
2. fail fast with an actionable message when interactive authorization blocks
   the HTTP client;
3. support the maintained browser-download workflow by validating files placed
   in an HMDB snapshot and generating a complete, restorable `manifest.lock`;
4. preserve official asset names, source URLs, byte counts, and SHA-256 values
   without moving HMDB parsing or integration into `biofetch`.

The maintained HMDB 5.0 core snapshot is:

```text
hmdb/database/5.0/
  raw/
    hmdb_metabolites.zip
    hmdb_proteins.zip
    structures.zip
  logs/
  manifest.lock
```

The current CephFS files were inspected on 2026-07-27:

| Asset | File | Bytes | Expected archive member | CRC result |
| --- | --- | ---: | --- | --- |
| `metabolites` | `hmdb_metabolites.zip` | 953,913,010 | `hmdb_metabolites.xml` | pass |
| `proteins` | `hmdb_proteins.zip` | 36,426,998 | `hmdb_proteins.xml` | pass |
| `structures` | `structures.zip` | 96,479,839 | `structures.sdf` | pass |

These observed byte counts are acceptance evidence for the current files, not
fixed size constraints for every HMDB 5.0 download.

## Non-goals

- Do not solve, evade, or automate Cloudflare challenges or CAPTCHA.
- Do not scrape individual HMDB HTML records as a substitute for the official
  bulk exports.
- Do not copy browser cookies into manifests, logs, traces, or command history.
- Do not treat `--insecure` as authentication; it only disables TLS
  certificate verification.
- Do not silently substitute an unofficial mirror.
- Do not parse XML/SDF or create cross-database mappings in `biofetch`;
  `bioextract` owns those derived products.

## Current failure and root cause

`biofetch hmdb database fetch` currently requests the official
`/system/downloads/current/` URLs with the shared Go HTTP client. The observed
response is `403 Forbidden` with `server: cloudflare` and
`cf-mitigated: challenge`. A browser user agent and referer do not satisfy the
managed JavaScript and cookie challenge. Retrying the same request five times
cannot change that authentication state.

The browser workflow can place valid files in `raw/`, but the first
`bulkasset lock` currently builds its source with no declared assets. As a
result, it can hash files while losing the declared asset name and source URL
needed by a future `restore`.

## Public CLI contract

Keep the published hierarchy:

```text
biofetch hmdb database fetch
biofetch hmdb database lock SNAPSHOT
biofetch hmdb database restore SNAPSHOT
```

The supported browser acquisition flow is:

```bash
# Complete HMDB's authorization in a browser and save the three files under:
# <snapshot>/raw/

biofetch hmdb database lock \
  /cephfs_data/genostack_v3/genostack_php/public_file_data/database/bioinfo/resources/hmdb/database/5.0
```

`fetch` remains a network acquisition action. It must not silently reinterpret
an untracked file as downloaded or locked. `lock` is the explicit trust
boundary that validates manually acquired files and records their content
identity.

## Affected components

| Component | Responsibility |
| --- | --- |
| `internal/shared/httpx` | Preserve HTTP status and selected non-secret response metadata in a typed error. |
| `internal/shared/staticasset` | Allow a source-specific error classifier to stop retrying permanent authentication/challenge failures. |
| `internal/shared/bulkasset` | Supply declared assets to first-time `lock` so matching paths retain names, URLs, and verification hooks. |
| `internal/hmdb` | Declare the core archive contract, recognize the HMDB challenge error, and provide the user-facing recovery message. |
| `internal/biofetch/cli_test.go` | Preserve the public HMDB `fetch|lock|restore` hierarchy and snapshot operand contract. |
| `docs/` | Document browser acquisition, authentication boundaries, and acceptance commands. |

## Execution slices

### Slice 1: declared-asset lock metadata

Change the bulk-asset lock path to build the source from the declared
`AssetSpec` values for the resolved snapshot version rather than from an empty
asset list.

Required invariants:

- a file whose relative path matches a declared asset receives the declared
  asset name and resolved official URL;
- optional declared files are included only when present;
- `.part`, logs, manifests, and undeclared scratch files are not included in
  the HMDB raw snapshot;
- an existing manifest remains a valid metadata source during a rebuild;
- other bulk-asset command families retain their current paths and lock
  behavior.

Acceptance:

- an offline fixture containing the three HMDB files creates exactly three
  manifest records;
- every record has the expected asset, `raw/` path, official URL, byte count,
  and SHA-256;
- `restore` consumes that manifest without requiring source declarations to be
  rediscovered.

### Slice 2: HMDB archive validation

Add a reusable ZIP structural verifier and attach it to the HMDB assets. Reuse
the same declaration for fetch-time and lock-time validation.

The core asset contract is:

| Asset | Path | Required archive member |
| --- | --- | --- |
| `metabolites` | `raw/hmdb_metabolites.zip` | `hmdb_metabolites.xml` |
| `proteins` | `raw/hmdb_proteins.zip` | `hmdb_proteins.xml` |
| `structures` | `raw/structures.zip` | `structures.sdf` |

The verifier must reject:

- an HTML challenge page saved with a `.zip` suffix;
- a truncated or unreadable ZIP central directory;
- a ZIP missing its required member;
- a path that is a directory or symbolic substitution instead of the selected
  regular file.

SHA-256 remains the immutable content identity. ZIP validation establishes
format and expected contents; it does not replace the manifest checksum.

Acceptance:

- valid one-member fixtures pass;
- HTML, truncated ZIP, and wrong-member fixtures fail before manifest write;
- the three real CephFS archives pass a read-only validation;
- no test writes to CephFS.

### Slice 3: fetch authentication failure semantics

Represent non-success HTTP responses with a typed error carrying status code
and a small allowlist of diagnostic headers. Do not retain response cookies,
authorization headers, or challenge tokens.

For HMDB:

- `401`, ordinary `403`, and `cf-mitigated: challenge` are non-retryable;
- a Cloudflare challenge produces an HMDB-specific recovery message naming the
  target `raw/` directory and the subsequent `lock SNAPSHOT` command;
- transient `408`, `429`, and `5xx` behavior remains governed by the existing
  retry policy;
- `--insecure` does not alter authentication classification.

Acceptance:

- an offline challenge fixture is requested once even when
  `--max-attempts 5` is configured;
- its error points to browser download and `lock`;
- retryable fixtures still exercise the existing retry count;
- error and trace output contain no cookies or challenge tokens.

### Slice 4: authorized machine credentials, only when specified upstream

Do not implement speculative Cloudflare-cookie replay. If HMDB supplies a
documented token, Basic/Bearer credential, stable bulk endpoint, or IP
allowlist, add the narrow corresponding adapter.

Any credential interface must:

- read secrets from a restricted file or environment variable, not a literal
  command-line value;
- apply credentials to range/resume requests as well as the initial request;
- redact them from logs, errors, traces, and manifests;
- record the official content URL and non-secret acquisition mode;
- include an offline redaction and resume test.

This slice is blocked until HMDB provides a stable, authorized machine-access
contract. It is not required for the browser acquisition and lock workflow.

## Compatibility

The command names and snapshot layout remain compatible. The intended behavior
changes are:

- permanent HMDB authorization failures stop after one attempt instead of five;
- first-time bulk locks gain declared asset names and URLs;
- invalid HMDB ZIP files fail lock instead of receiving a manifest record.

Existing valid manifests remain readable. `restore` continues to require exact
SHA-256 equality and must reject changed content served by a moving `current`
URL.

## Verification

The implementation must pass:

```bash
GOCACHE=/tmp/biofetch-test go test ./...
GOCACHE=/tmp/biofetch-test go vet ./...
GOCACHE=/tmp/biofetch-test go build -o /tmp/biofetch ./cmd/biofetch
```

Real-resource acceptance is separate from default tests:

```bash
/tmp/biofetch hmdb database lock \
  /cephfs_data/genostack_v3/genostack_php/public_file_data/database/bioinfo/resources/hmdb/database/5.0 \
  --dry-run
```

After reviewing the dry-run, an authorized non-dry lock must be read back to
confirm:

- `database = "hmdb"`;
- `asset = "database"`;
- `version_token = "5.0"`;
- exactly the intended files appear;
- asset names, official URLs, byte counts, and SHA-256 values are populated;
- no credential or browser-session material appears.

## Risks and rollback

- Full ZIP CRC and SHA-256 validation reads approximately 1.1 GB from CephFS;
  keep it in explicit lock/acceptance paths, not CLI startup.
- A moving official `current` URL may later serve different bytes. This is
  expected to make restore fail safely against the old SHA-256.
- If the shared bulk lock change affects another family, revert that slice
  without changing HMDB files; no snapshot mutation is required before the
  final lock command.
- The manually downloaded raw files remain the recoverable source artifact
  throughout implementation.

## Intended delivery

One implementation PR may contain three semantic commits:

1. preserve declared metadata during bulk-asset lock;
2. validate HMDB archives and classify authorization failures;
3. update contract tests and documentation evidence.

The credential slice is a later PR only after an official machine-access
mechanism is known.
