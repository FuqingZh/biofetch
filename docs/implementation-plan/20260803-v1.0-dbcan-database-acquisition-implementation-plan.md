# dbCAN database acquisition implementation plan

Version: v1.0
Date: 2026-08-03
Status: implemented; full-size lock verified; restore/publication acceptance pending
Estimate: 4-6 engineer-days

## Goal

Add a reproducible, raw-only dbCAN CAZyme database snapshot that:

1. exposes `biofetch dbcan database fetch|lock|restore`;
2. uses the upstream product name `database`, matching the official
   `run_dbcan database` command;
3. pins the first release to the official S3 token
   `db_v5-2-9_5-5-2026`, without resolving or falling back to the moving
   `db_current` HTTP snapshot;
4. treats the four maintained CAZyme files as one required, atomic collection;
5. records exact source URLs, byte counts, and local SHA-256 values in
   `manifest.lock`; and
6. makes multi-gigabyte resume and chunking safe before using them for the
   6.93 GiB collection.

This plan is implementation authority for the first dbCAN database acquisition
slice. The maintained
[resource and manifest contract](../architecture/resource-manifest-contract.md),
[dual-omics acquisition design](../architecture/20260724-v1.0-dual-omics-resource-acquisition-design.md),
and [test contract](../testing/20260717-v1.0-test-contract.md) remain authority
for shared layout, ownership, compatibility, and validation rules.

## Non-goals

- Do not use, probe as a fallback, or lock content from the mutable
  `db_current` snapshot.
- Do not scrape CAZy or claim that the run_dbCAN GPL-3.0 software license grants
  redistribution rights for every downloaded database record.
- Do not download CGC assets in this slice. A later, separately specified
  `biofetch dbcan cgc` family may own that collection; do not add an ambiguous
  `--cgc` switch to `dbcan database`.
- Do not run `hmmpress`, construct DIAMOND databases, unpack PUL archives, or
  otherwise install or transform upstream assets.
- Do not parse mappings, normalize identifiers, or integrate dbCAN with CAZy,
  KEGG, Rhea, UniProt, or another database. Those are downstream concerns.
- Do not create `tidy/`, indexes, pressed-HMM sidecars, or unpacked PUL trees.

## Authority and evidence

The upstream contract was checked on 2026-08-03 against these official
sources:

- run_dbCAN's
  [v5.2.9 database constants](https://github.com/bcb-unl/run_dbcan/blob/v5.2.9/dbcan/constants/databases_constants.py)
  define `S3_DATABASE_RELEASE = "db_v5-2-9_5-5-2026"`, the S3 base URL,
  the four CAZyme URLs, and the local `dbCAN-sub.hmm` spelling;
- the official
  [database downloader](https://github.com/bcb-unl/run_dbcan/blob/v5.2.9/dbcan/utils/database.py)
  selects the CAZyme collection independently of CGC files and demonstrates
  resume behavior, while also showing why biofetch needs stronger immutable
  identity and response validation;
- the official
  [v5.2.9 release](https://github.com/bcb-unl/run_dbcan/releases/tag/v5.2.9)
  anchors the software release associated with the constants; and
- the official dbCAN
  [release directory](https://pro.unl.edu/dbCAN2/browse_download.php?path=run_dbCAN_database_total/db_v5-2-9_5-5-2026)
  exposes the pinned database token and files.

The S3 `Content-Length`, `ETag`, and `Last-Modified` headers were observed by
read-only HEAD requests on 2026-08-03. The official core four-file download
contract publishes no SHA-256 or MD5 sidecar. The byte counts below are fixed
first-release expectations and must also be checked from response metadata and
the completed local files. ETags and dates are discovery evidence only. In
particular, the multipart S3 ETag for `dbCAN_sub.hmm` is a generation validator,
not an MD5 checksum. SHA-256 of local content remains the biofetch integrity
identity for every asset.

## Implementation outcome and evidence-driven changes

The implementation completed the public CLI, fixed snapshot, HTTP safety,
atomic collection, strict lock/restore, offline tests, and the default online
smoke. On 2026-08-03, HEAD and `Range: bytes=0-0` passed for all four pinned
URLs, including exact advertised lengths and `Content-Range` totals. It is
intentionally not called production-ready because the separately authorized
7,439,565,906-byte release acceptance has not run.

Current-code validation changed two internal paths without changing the public
or safety invariants:

- `staticasset` already supported incremental manifests needed by existing
  non-atomic families. Complete-collection and immutable-restore behavior is
  therefore an explicit source policy used by dbCAN rather than a global
  removal of compatible incremental behavior.
- A Range-ignored response is closed without reading its body, its stale
  partial file is removed, and a typed retryable error is returned. The normal
  caller attempt loop performs the next clean request, so one attempt never
  hides an extra full-body request and the configured attempt budget remains
  auditable.

The delivered shared implementation binds chunk state to final URL, content
length, ETag and Last-Modified; sends a strong ETag or Last-Modified through
`If-Range`; strictly validates `Content-Range`; resets stale chunks; applies one
limiter to HEAD, probe, range, and full requests; and honors bounded
`Retry-After` for 429/503 responses.

## Public CLI contract

```text
biofetch dbcan database fetch
biofetch dbcan database lock SNAPSHOT
biofetch dbcan database restore SNAPSHOT
```

The first fetch contract is deliberately fixed:

```bash
biofetch dbcan database fetch \
  --version db_v5-2-9_5-5-2026 \
  --allow-large-downloads \
  --output /data/resources/dbcan
```

- Omitting `--version` uses the compiled-in fixed token
  `db_v5-2-9_5-5-2026` without contacting a release-resolution endpoint.
- An explicit `--version` must equal `db_v5-2-9_5-5-2026`. Reject the literal
  selectors `current`, `latest`, and `db_current`, and every other token,
  before network access or filesystem creation.
- Fetch help must display `db_v5-2-9_5-5-2026` as the fixed default and state
  that moving/latest selectors are unsupported.
- Do not expose asset selection for this atomic collection. In particular,
  `--assets`, `--cgc`, and `--no-cgc` are not part of this public contract.
- Outer file workers default to `1`. Existing retry, request interval,
  progress, dry-run, existing-file, TLS, and log flags retain their shared
  spelling and semantics where applicable.
- `lock` and `restore` take one exact snapshot operand and expose neither
  `--output` nor `--version`.
- `restore` remains the repository term; do not reintroduce `sync`.

## Snapshot path and manifest contract

```text
<resource-root>/dbcan/database/db_v5-2-9_5-5-2026/
  raw/
    CAZy.dmnd
    dbCAN.hmm
    dbCAN-sub.hmm
    fam-substrate-mapping.tsv
  logs/
  manifest.lock
```

The manifest common envelope is:

```toml
database = "dbcan"
asset = "database"
source = "run-dbcan-s3"
version = "5.2.9"
version_token = "db_v5-2-9_5-5-2026"
```

Each of exactly four `[[files]]` records contains its stable logical asset
name, canonical `raw/...` path, exact pinned S3 URL, actual bytes, and local
SHA-256. The kebab-case `source = "run-dbcan-s3"` identifies the acquisition
channel consistently with existing repository source values. `version =
"5.2.9"` records the associated run_dbCAN software release, while
`version_token` remains the immutable database directory token. The local
hyphenated `dbCAN-sub.hmm` path and remote underscored `dbCAN_sub.hmm` URL must
both survive lock and restore.

`lock SNAPSHOT` derives and validates the token from the final path segment,
requires exactly the four declared regular files, rejects undeclared content
under `raw/`, hashes all four current files, and publishes no lock on any
missing, extra, size-mismatched, unreadable, or hashing-failed file. It neither
contacts upstream nor trusts an old lock to redefine version, paths, URLs, or
the required set.

`restore SNAPSHOT` reads only that snapshot's complete manifest. It downloads
each exact recorded URL, verifies the completed file against the recorded
SHA-256 and byte count, and fails safely if upstream bytes drift. It performs
no token resolution, URL reconstruction, S3-to-HTTP fallback, or partial-lock
recovery.

## Affected components

| Component | Planned responsibility |
| --- | --- |
| `internal/shared/httpx` | Make single-resume and chunked transfers prove the requested interval and stable remote identity; honor shared request limiting and retry timing without consuming ignored-Range bodies. |
| `internal/shared/staticasset` | Apply the limiter to every transfer request, carry retry timing, verify final bytes/SHA, and withhold collection completion until all required assets exist. |
| `internal/shared/bulkasset` | Express a fixed-version, all-required, all-large collection with outer workers defaulting to one and strict lock/restore behavior. |
| `internal/dbcan` | Declare the CLI family, pinned source, four URLs, remote/local name mapping, expected byte counts, and strict version validator. |
| `internal/biofetch` | Register the family and protect the public command/flag contract. |
| `docs/` | Keep the plan, authority index, and dual-omics status/scale/risk synchronized. |

Reuse these components rather than creating a dbCAN-only downloader. Shared
hardening is a dependency because it protects every large HTTP asset and the
first dbCAN fetch would otherwise amplify current edge cases.

## Dependency-ordered execution slices

### Slice 1: harden HTTP range and remote-identity behavior

Update `httpx` before adding dbCAN:

- if a GET with `Range` receives `200 OK`, close the body immediately; do not
  read or discard the multi-gigabyte response merely to discover that Range
  was ignored;
- for `206 Partial Content`, require a parseable `Content-Range` whose start,
  end, and total match the requested interval and probed object length;
- reject missing, malformed, shifted, truncated, overlong, or total-mismatched
  `Content-Range` before writing or appending bytes;
- bind resumable chunk state to a remote identity captured during the probe,
  using the final URL plus content length and a strong validator when the
  server supplies one (`ETag` preferred, otherwise `Last-Modified`);
- discard or quarantine stale chunk state when that identity changes, rather
  than combining chunks from different object generations;
- attach `If-Range` when a suitable validator exists and treat identity drift
  as a clean failure/restart decision, never as appendable content;
- route HEAD, range probes, chunks, retries, and ordinary GETs through the same
  request limiter; and
- parse bounded `Retry-After` delta-seconds or HTTP dates for `429` and
  retryable `503`, combining it with configured backoff without bypassing the
  limiter or exceeding the attempt budget.

The response body may be read only after status, interval, and identity
validation. A failed chunk must not be marked done, and merge occurs only after
every chunk is revalidated by exact size.

### Slice 2: add an atomic-completion gate to shared assets

Extend `staticasset`/`bulkasset` narrowly so a collection can require all
declared files and reject undeclared files:

- partial progress may remain as `.part`/`.parts` scratch state for resume;
- an interrupted fetch must not leave a `manifest.lock` that advertises a
  complete dbCAN snapshot;
- the final manifest is written only after all four final files pass required
  path, expected-byte, and SHA-256 checks;
- lock uses the same complete declared inventory and rejects extra raw files;
- restore rejects an empty, partial, duplicate-path, duplicate-asset, unsafe,
  or wrong-identity manifest before any network or final-file mutation; and
- a checksum or size failure removes the invalid completed temporary file so a
  later run cannot reuse it as valid.

Preserve incremental progress internally only if it is unambiguously marked
incomplete and cannot be consumed by restore or aggregate manifest building.

### Slice 3: declare dbCAN database and public CLI

Add `internal/dbcan` using `bulkasset` with:

- `Database: "dbcan"`, `Asset: "database"`;
- fixed token `db_v5-2-9_5-5-2026` and upstream software version `5.2.9`;
- four default, required, large assets and no selectable subset;
- exact S3 URLs and the `dbCAN_sub.hmm` to `dbCAN-sub.hmm` mapping;
- expected total and per-file byte counts as named release constants;
- strict declared-only lock behavior; and
- outer download workers defaulting to `1` while `httpx` owns bounded internal
  chunk parallelism.

Register it in the root command and add the CLI contract tests. Help must state
the approximately 6.93 GiB cost, fixed release, all-file requirement, and the
large-download opt-in.

### Slice 4: exact lock and restore semantics

Add focused dbCAN tests and any shared checks necessary to prove:

- first-time lock assigns all exact URLs and logical asset names without an
  old manifest or network access;
- lock rejects wrong snapshot tokens and every incomplete or expanded layout;
- restore accepts only the exact four-record lock and exact URLs;
- restored files are promoted atomically only after exact byte and SHA-256
  verification; and
- upstream drift, identity change during chunking, and checksum mismatch leave
  no false final record or complete manifest.

### Slice 5: documentation and read-only real-source acceptance

Update maintained CLI/resource/test documentation in the implementation PR.
Run the HEAD plus one-byte Range online smoke against the official pinned S3
objects in the default PR gate and keep any captured headers under temporary
local storage. The full real download remains outside default CI because of its
7,439,565,906-byte storage and transfer cost, but becomes a mandatory release
acceptance after separate storage authorization and before the implementation
is called production-ready or any CephFS publication occurs.

## Compatibility

This adds a new command family and snapshot identity; no existing dbCAN CLI or
manifest exists to migrate. Existing command names, manifest schema, aggregate
manifest format, and `staticasset` manifests remain readable.

Shared HTTP behavior becomes stricter by design: servers that return invalid
partial responses, ignore Range on a large probe, or change remote identity can
no longer be resumed as if immutable. Such transfers restart cleanly or fail
with actionable diagnostics. Valid `200` full downloads and valid `206`
resumes remain supported. `restore` continues to mean exact manifest replay,
not latest-content retrieval.

CGC remains compatible as a future sibling asset, `biofetch dbcan cgc`, with
its own complete inventory, scale gate, plan, and manifest. Adding that sibling
must not change the meaning of existing `dbcan database` locks.

## Risks and mitigations

| Risk | Mitigation and required evidence |
| --- | --- |
| Range-ignoring origin sends a full 5.13 GB body per probe/chunk | Validate status before body consumption and test that the fixture observes prompt close with zero payload copied. |
| A multipart S3 ETag is mistaken for a content checksum | Use it only as a remote-generation validator; always record and enforce local SHA-256. |
| Remote object changes between probe or resumed chunks | Bind state to final URL, length, and validator; fail/restart on any change and never merge generations. |
| Four outer downloads multiply chunk concurrency and saturate storage/network | Default outer workers to one; keep internal chunk concurrency bounded and race-tested. |
| Partial success becomes an apparently complete snapshot | Publish the authoritative lock only after the all-required-assets completion gate. |
| `lock` blesses a hand-curated subset or derived sidecars | Require exactly four declared paths and reject extras, including hmmpress outputs. |
| Moving `db_current` defeats reproducibility | Do not support or fall back to it; compile and test exact pinned S3 URLs. |
| Retry storms or S3 throttling | Apply one request limiter to every request and honor bounded `Retry-After`. |
| CAZy/dbCAN provenance is overstated | Preserve source identity, avoid CAZy scraping, and keep redistribution/legal review outside downloader entitlement logic. |
| Full fixtures make default tests slow or network-dependent | Use sparse/small `httptest` payloads with lowered chunk thresholds; keep live acceptance explicit and read-only. |

## Recovery and rollback

- Before the completion gate, resume only scratch state whose recorded remote
  identity still matches. Otherwise remove that scratch state and start the
  affected file from byte zero.
- On a failed fetch or restore, keep already verified final files available for
  SHA-based reuse, but leave no new complete `manifest.lock` unless the entire
  declared collection is valid.
- On SHA-256, byte-count, or remote-identity drift, remove the invalid completed
  temporary file and retain the prior authoritative lock unchanged.
- If shared HTTP hardening regresses another source, revert the dbCAN command
  slice and the incompatible helper slice together. No manifest migration or
  resource-tree deletion is required.
- A published `db_v5-2-9_5-5-2026` lock is immutable. A future upstream build
  requires a new reviewed token and manifest, never replacement behind the old
  directory.

## Exact verification gates

### Focused offline tests

Add and pass tests that prove all of the following:

1. CLI exposes only `dbcan database fetch|lock|restore`; exact snapshot
   operands and kebab-case flags work; `sync`, `--cgc`, `--no-cgc`, asset
   subsets, `db_current`, and arbitrary versions are rejected.
2. Large opt-in and fixed-version validation fail before network calls and
   filesystem creation; the default outer worker count is one.
3. The source resolves exactly four URLs and paths, including the remote
   underscore/local hyphen rename, with expected per-file and total bytes.
4. A Range-ignored response is closed without consuming its full body;
   malformed/missing/wrong `Content-Range` fails before a chunk write.
5. Chunk resume succeeds with matching URL, length, validator, ranges, and
   exact sizes; any validator or total-length change invalidates old chunks.
6. Every HEAD, probe, chunk, and retry passes through the request limiter;
   `Retry-After` delta/date behavior is deterministic under a fake clock or
   bounded test timing.
7. Fetch failure after one to three assets leaves no consumable complete lock;
   a later run reuses only SHA-verified final files and finishes all four.
8. Lock is offline, hashes all bytes, requires exactly four files, records
   exact URLs, and rejects missing, extra, wrong-token, symlink/unsafe, or
   size-mismatched layouts.
9. Restore rejects partial/wrong manifests before requests and verifies exact
   URL, byte count, and SHA-256 before atomic promotion; drift fails without a
   false final record.
10. Chunk and outer-worker concurrency passes the race detector and completed
    chunk workspaces are removed.

### Default PR online smoke

Without downloading object bodies, verify all four fixed URLs by HEAD and a
bounded one-byte range request. Require `200` HEAD, the expected
`Content-Length`, stable validator metadata, `206` for `bytes=0-0`, and exact
`Content-Range: bytes 0-0/<expected-total>`. This acceptance must not write
CephFS and should write any captured headers only under `/tmp`. It is a required
default PR gate, not an optional manual check.

### Production-ready release acceptance

A full 7,439,565,906-byte acquisition is excluded from default CI, but it is
mandatory after separate suitable-storage authorization and before declaring
the implementation production-ready or publishing a dbCAN snapshot to CephFS.
It must confirm four final paths, exact byte counts, SHA-256 manifest records,
no scratch workspace, a successful exact restore/readback, and aggregate
manifest inclusion. Record the resulting SHA-256 values as release evidence;
the upstream core contract has no checksum sidecars, and observed ETags must
not be converted into MD5 or manifest hashes.

For the documentation change itself, validate every relative Markdown link and
run:

```bash
git diff --check
```
