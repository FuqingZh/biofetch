# KEGG PATHWAY sharded and bounded download implementation plan

Version: v1.0
Date: 2026-08-20
Status: implemented and merged; production rollout pending

## Goal

Make long-running `biofetch kegg pathway fetch` operations bounded,
restartable, and faster without changing the KEGG PATHWAY snapshot layout or
allowing independent processes to race on one `manifest.lock`.

The implementation adds:

- one repeatable, comma-separated organism-prefix selector;
- a finite per-request timeout that activates the existing retry policy;
- bounded organism-level workers sharing one global request limiter; and
- atomic manifest checkpoints during a long multi-organism run.

The intended operating model is one process per snapshot. Prefixes run in the
requested order; organisms within the active prefix may run concurrently.

## Current behavior and problem

The current PATHWAY command accepts explicit organisms, all organisms, or the
reference scope. `--all-organisms` resolves `/list/genome`, chunks the resulting
organism codes into groups of 32, and processes every organism and every
download serially. The batch boundary currently changes logging only;
`manifest.lock` is written after the complete command finishes.

The KEGG HTTP client currently has no finite timeout. `--max-attempts` and
`--retry-wait` apply only after a request returns an error, so an in-flight
request can remain stuck indefinitely and never enter retry handling.

Completed final files already provide a useful restart boundary:

- a valid record in the existing manifest is reused without rehashing;
- a non-empty final file absent from the manifest is hashed and reused; and
- current records are merged with still-present records from the existing
  manifest before the lock is replaced atomically.

This is file-level restart, not a promise of byte-level resume. KEGG endpoints
may ignore HTTP Range requests; when they do, a partial `.part` file must be
discarded or restarted while previously completed final files remain reusable.

## Public CLI contract

### Prefix selection

Add a list-valued option using the spelling requested for this workflow:

```text
--organism-prefix string
--organism-prefix-file file
```

Accepted forms include:

```bash
--organism-prefix a
--organism-prefix a,b,c
--organism-prefix a --organism-prefix b
--organism-prefix-file prefixes.txt
```

The contract is:

- tokens are trimmed, lowercased, deduplicated by first occurrence, and must
  each be exactly one ASCII letter from `a` through `z`;
- prefix order preserves first-seen input order;
- the prefix matches the first byte of the normalized KEGG organism code, not
  the scientific name;
- one `/list/genome` response is resolved for the command, then partitioned by
  the requested prefixes;
- each requested prefix must match at least one organism or validation fails
  before PATHWAY assets are downloaded;
- `--order` continues to control organism and pathway traversal within each
  prefix, but does not reorder the prefix plan; and
- the command logs the number of matched, completed, and skipped organisms for
  every prefix.

`--organism-prefix` is a fourth scope selector and is mutually exclusive with
`--organisms`, `--all-organisms`, and `--include-reference`. It cannot be
combined with `--pathway-ids`, because one prefix selects multiple organisms.

No prefix selection is treated as proof of a complete all-organism inventory.
Running all 26 letters covers the alphabetic organism codes returned by that
command's `/list/genome` response; completeness is determined from that exact
catalog response rather than a permanently assumed upstream naming rule.

### Timeout

Add:

```text
--request-timeout duration   default 60s
```

The value must be greater than zero. It applies to each KEGG PATHWAY HTTP
request, including response-body reads. A timeout is retryable and consumes one
of the existing `--max-attempts`; it does not introduce a second retry loop.
PATHWAY uses strict metadata probes for the first `N-1` attempts and skips the
probe on the final attempt so that the last attempt is exactly one GET request.
The shared `httpx` downloader exposes this as an opt-in, zero-default option;
other downloaders retain their existing metadata-probe behavior.

The timeout is configured only for KEGG PATHWAY fetch in this slice. Do not
change the zero-timeout default of the shared `httpx.NewClient`, because that
would alter unrelated database downloaders.

### Download workers

Add:

```text
--workers int   default 1, accepted range 1-8
```

The conservative default preserves current serial behavior. `--workers 4` is
the first recommended production canary. The option applies to explicit
multi-organism, prefix, and all-organism PATHWAY scopes. A reference or
single-organism run may use the same engine but receives little or no benefit.

Workers operate at organism scope. A worker owns one `raw/<organism>/`
directory at a time and processes that organism's planned assets serially.
There is no nested asset-level download worker pool.

All workers share one thread-safe request limiter. The configured
`--request-interval` is a minimum interval between request start times across
the whole process, not per worker. At the current 350 ms default, the
theoretical aggregate start-rate ceiling remains approximately 2.86 requests
per second. Workers improve throughput by overlapping response latency; they
do not authorize a higher request rate.

## Execution and checkpoint protocol

The controller performs these steps:

1. Resolve optional `/info/pathway` metadata and assign the snapshot token.
2. Resolve the selected scope. Prefix mode downloads `/list/genome` once,
   validates every requested prefix, and builds ordered prefix groups.
3. Process prefix groups sequentially. For non-prefix multi-organism modes,
   process one ordered organism stream.
4. Partition the active stream into the existing 32-organism batches.
5. Map each batch through a bounded ordered worker pool. Each worker writes only
   its own organism directory and returns records plus planning statistics.
6. The controller merges successful records with the existing manifest,
   removes records whose final files no longer exist, sorts deterministically,
   and atomically replaces `manifest.lock` after every completed batch.
7. At a prefix boundary, emit the prefix summary only after its final batch
   checkpoint succeeds, then advance to the next prefix.
8. Refresh optional end metadata and write the final manifest and run summary.

Workers never write `manifest.lock`. Ordered result collection and the existing
record sort keep manifest records independent of worker completion order.

If the process is interrupted after final files are renamed but before the next
checkpoint, a rerun hashes and adopts those files. The maximum manifest lag is
one active batch, not the entire command.

## Failure policy

The existing narrow skip policy remains authoritative, extended to bounded
timeouts as follows:

| Request | Retryable conditions | Exhausted behavior |
| --- | --- | --- |
| `/list/genome` needed for prefix or all-organism selection | timeout and existing transient transport/status conditions | fail command; membership is unknown |
| `/list/pathway/<organism>` | timeout and existing retryable transport/status conditions; 403/404 remain unavailable-scope conditions | warn, count, and skip that organism after retry exhaustion or an immediate non-retryable unavailable response |
| pathway entry | timeout, retryable transport/status conditions, and existing 403 handling | warn and skip asset |
| KGML, conf, and image | timeout plus existing retryable and unavailable conditions | warn and skip asset |
| reference pathway list | timeout plus existing retryable conditions | fail command; do not weaken reference scope |
| optional `/info/pathway` metadata | timeout plus existing retryable conditions | warn and continue without claiming unavailable metadata |

Retries from different workers still pass through the shared request limiter.
An error cancels undispatched work, while already-running workers are bounded by
the request timeout. Completed final files remain observable and reusable.

## Snapshot and compatibility invariants

This change does not alter:

- `kegg/pathway/<version_token>/raw/<organism>/...` paths;
- the `manifest.lock` schema;
- supported PATHWAY asset names or the default asset set;
- existing `--organisms`, `--all-organisms`, `--include-reference`, `--assets`,
  `--order`, `--on-existing`, retry, interval, TLS, dry-run, or log options;
- lock and restore command operands; or
- the responsibility boundary between raw acquisition and downstream parsing.

Repeated prefix invocations against the same snapshot merge exact existing and
current file records. Manifest scope continues to be derived from actual
recorded `raw/<scope>/` paths, not from a claim that a requested prefix was
complete.

Multiple operating-system processes must not write the same snapshot. This
slice supports concurrency only inside one controller process. True
multi-process or multi-host acquisition would require isolated shard snapshots,
a defined merge command, catalog identity, and an additional completeness
contract; it is not part of this plan.

## Implementation slices

### Slice A: selector and bounded request contract

Predecessors: none.

Implement the new configuration fields, list flags, validation, prefix catalog
partitioning, and KEGG PATHWAY-only timeout. Preserve the existing three scope
paths and error messages except where the new fourth scope must be named.

Verification:

- inline, repeated, and file prefix inputs preserve first-seen order;
- uppercase normalization and duplicate removal are deterministic;
- empty, multi-character, numeric, and non-ASCII prefixes fail;
- scope conflicts and `--pathway-ids` conflicts fail before directory creation;
- one catalog request serves all requested prefixes;
- a requested prefix with no catalog match fails before PATHWAY asset requests;
- a timed-out request enters exactly the configured number of attempts; and
- unrelated KEGG commands retain their existing client timeout.

Acceptance: the public flags parse through the root command, offline fixtures
prove exact selection, and no snapshot layout or manifest schema changes.

### Slice B: bounded organism concurrency

Predecessor: Slice A.

Replace the PATHWAY client's unsynchronized last-request timestamp with one
shared request limiter, then map organism batches through the existing ordered
parallel helper. Keep asset downloads within each organism serial.

Verification:

- active organism work never exceeds `--workers`;
- workers 1, 4, and 8 produce the same final file set and deterministic
  non-time manifest fields;
- recorded request start times remain at least the configured interval apart
  across all workers and retries;
- different workers never write the same path;
- an injected failure stops undispatched work and running requests finish or
  time out; and
- race detection passes for `internal/kegg` and the shared limiter path.

Acceptance: `--workers 1` preserves serial semantics and higher values overlap
latency without multiplying the configured request-start rate.

### Slice C: restart and checkpoint publication

Predecessor: Slice B.

Move the existing complete-record merge and atomic manifest write to a reusable
controller checkpoint, invoked after each 32-organism batch and at final
completion. Do not let workers publish the lock.

Verification:

- interruption after a completed batch leaves an exact readable manifest;
- interruption after final-file rename but before checkpoint reuses and adopts
  that file on rerun;
- stale manifest records whose files are missing are removed;
- a completed prefix is checkpointed before the next prefix starts;
- an error never publishes a record for a partial file; and
- Range-ignored fixtures restart the current file without redownloading prior
  final files.

Acceptance: rerunning the same prefix plan with `--on-existing skip` schedules
only missing or invalid files and converges to the same complete file records.

### Slice D: public documentation and operational canary

Predecessors: Slices A-C.

Update the current architecture, testing, README, and changelog documents from
the implemented behavior. Do not publish planned defaults as delivered before
the executable tests pass.

Run an explicitly authorized live canary only under `/tmp`, using a small
current prefix and a reduced asset set before any full asset run. Compare
workers 1 and 4 using the same catalog response or immediately repeated run,
verify final hashes and manifest records, inspect retry/rate-limit warnings,
and report the input, environment, elapsed time, and output equivalence. Do not
claim a speedup without that measurement.

Acceptance: offline gates pass and the canary demonstrates bounded progress,
equivalent output, and no effective request-interval violation.

## Risks and controls

| Risk | Control |
| --- | --- |
| Workers accidentally multiply the request rate | One shared limiter gates every request and retry; test request timestamps |
| Concurrent code races on client state or records | Remove mutable unsynchronized timestamps; ordered worker results; race gate |
| Worker completion order changes manifests | Controller-only checkpoints and deterministic record sorting |
| A checkpoint makes a partial selection appear globally complete | Scope remains exact recorded paths; no prefix-complete field or all-organism claim |
| Frequent large manifest writes perform poorly on CephFS | Reuse the 32-organism batch boundary; measure before reducing checkpoint size |
| Timeout is too small for an unusual response | Expose a positive duration override; default 60s; test longer configured values |
| Upstream ignores Range | Promise only final-file restart; retain `.part` safety and reuse prior final files |
| Users launch many prefix processes anyway | Document one-process ownership and provide multi-prefix input in one command |
| Alphabetic prefixes become incomplete upstream | Derive membership from the command's catalog and avoid equating prefix selection with `all` |

## Rollback and cleanup

The feature is additive. A runtime rollback uses `--workers 1` and explicit
`--organisms`; removing the new flags does not require snapshot migration.
Existing final files and manifests remain compatible with the pre-change
binary.

Tests and canaries use temporary roots. Remove only the exact temporary canary
directory after output hashes and logs have been captured. Never clean or
rewrite a production snapshot as part of rollback.

## Delivery and review

The preferred review is one focused KEGG PATHWAY change because selector,
timeout, limiter, workers, and checkpoints jointly define the restart and rate
contract. If review size requires splitting, Slice A may be delivered first;
Slices B and C must remain together so concurrency cannot ship without a
single-writer checkpoint path.

Building or validating the repository does not deploy the CephFS production
binary. Copying a verified binary to the production scripts directory requires
separate authorization, followed by SHA256 and `biofetch --help` readback.

Implementation is not complete until the final gate and documentation updates
pass. Production rollout is not complete until the separately authorized
binary replacement and live version/help readback succeed.
