# GitHub publication readiness implementation plan

Version: v1.0
Date: 2026-08-13
Status: implementation complete on the local delivery branch; merge, tag, and first release remain pending
Estimate: 4-6 engineer-days, excluding upstream legal review

## Goal

Turn `FuqingZh/biofetch` from a functional internal production CLI into an
installable, secure, supportable, and auditable public GitHub repository without
changing its data-ownership boundary:

- `biofetch` downloads and locks upstream raw snapshots;
- upstream database content remains governed by each upstream provider;
- `biofetch` does not redistribute downloaded databases through GitHub
  releases; and
- normalized or integrated data remains outside this repository.

The first public release candidate is `v0.1.0`. Pre-1.0 versioning is deliberate:
the CLI is useful and tested, but the aggregate manifest has an intentional v2
schema break and the repository has never published a tagged release.

This plan is publication-readiness authority. Apache License 2.0 is the approved
license for repository-owned code and documentation. Approval of this plan does
not authorize changing GitHub security settings, publishing a tag/release, or
writing CephFS. Those external actions retain explicit owner gates.

## Execution status

The repository-local implementation is complete on the delivery branch. The
aggregate-v2 work that preceded this plan remains in the same reviewable scope;
it is not silently discarded or rewritten. Completed local artifacts include
the canonical module path, Apache-2.0 license, dependency notices, source and
release metadata, public contributor/security entrypoints, migration guidance,
fixed-SHA CI and CodeQL workflows, the release workflow, and bounded upstream
smoke probes. The PR smoke is wired to pull requests and remains strictly
metadata/range-only. GitHub repository description, topics, merged-branch cleanup,
Dependabot security updates, secret scanning, and push protection were enabled
and read back successfully.

The implementation branch is committed and pushed, and its exact head has
passed validation, CodeQL, and the required status check. The review fixes are
implemented, but GitHub still retains their review threads as unresolved
bookkeeping; closing those threads is an explicit owner/reviewer action. The
remaining gates are therefore delivery-state transitions rather than
unverified local implementation: resolve the addressed threads, merge to
protected `main`, then obtain separate authorization to create the immutable
`v0.1.0` tag and release. No database bytes or CephFS writes are part of this
implementation.

## Decisions and owner gates

### Code license

Decision: use **Apache License 2.0** for repository-owned code and
documentation. The owner approved this decision on 2026-08-13. It permits
commercial and proprietary downstream use, while providing an explicit patent
grant and standard license/notice obligations appropriate for a reusable
infrastructure CLI.

The code license does not apply to databases fetched by the CLI. Add a separate
upstream-data terms document stating that:

- GitHub releases contain only `biofetch` software and documentation;
- downloaded database files are not relicensed by this repository;
- users must comply with each upstream provider's access, use, citation, and
  redistribution terms; and
- `manifest.lock` provenance is not a redistribution authorization.

### Version policy

- Use Semantic Versioning for the CLI and aggregate-manifest contract.
- Publish `v0.1.0` as the first release after all gates below pass.
- Treat CLI removals, flag semantics, snapshot layout, and aggregate schema as
  compatibility surfaces.
- Before 1.0, record every breaking change in `CHANGELOG.md` and the relevant
  migration guide; after 1.0, require a major version.

### Supported platform

The first release supports Linux `amd64` and `arm64` with `CGO_ENABLED=0`.
macOS, Windows, Homebrew, Conda/Bioconda, containers, and package-manager
publication are deferred until an actual consumer requires them. Source builds
require the Go version declared by `go.mod`.

### Public Go surface

`biofetch` remains a CLI. Internal packages remain under `internal/`; this plan
does not create a public Go library API. Changing the module directive to
`github.com/FuqingZh/biofetch` makes `go install` work without committing to a
stable importable SDK.

## Non-goals

- Do not add more databases as part of publication readiness.
- Do not publish downloaded database content in GitHub Releases, packages, or
  caches.
- Do not add Docker, Kubernetes, a service runtime, staging environment,
  telemetry backend, wiki, or Discussions merely for repository appearance.
- Do not impose a numeric coverage threshold. Add tests where an actual public
  or source-definition contract is presently unprotected.
- Do not require a second reviewer while the repository has one maintainer.
  Keep the existing zero-approval PR rule, required CI, current-head policy, and
  review-thread resolution.
- Do not make CephFS deployment part of GitHub release automation.
- Do not publish `v0.1.0` while aggregate v2 remains only in a dirty local
  worktree or while its consumer gate is unresolved.

### Slice 6: build a verifiable release workflow

Predecessors: Slices 2-5.

Trigger and authorization:

- trigger on signed or maintainer-created `v*` tags and manual dry runs;
- reject tags not pointing to a commit reachable from protected `main`;
- use least-privilege workflow permissions and a dedicated release job;
- never read or write CephFS.

Artifacts for Linux `amd64` and `arm64`:

```text
biofetch_<version>_linux_amd64.tar.gz
biofetch_<version>_linux_arm64.tar.gz
checksums.txt
sbom.spdx.json
```

Each archive contains the binary, `LICENSE`, `THIRD_PARTY_NOTICES`, a short
release README, and shell completion files. The workflow must:

1. build with exact tag-derived version and `-trimpath`;
2. run the complete source gate before packaging;
3. inspect each binary with `go version -m`;
4. regenerate and verify `THIRD_PARTY_NOTICES` against the exact release module
   graph;
5. generate SHA256 checksums and an SPDX SBOM;
6. publish GitHub artifact attestations/provenance;
7. create release notes from `CHANGELOG.md`; and
8. upload only software/documentation artifacts, never database snapshots.

Acceptance before enabling automatic tag publication:

- a dry-run workflow on an exact commit produces both archives;
- archives unpack cleanly and contain only the declared files;
- third-party license notices match the exact dependency graph;
- checksums verify;
- both binaries execute `biofetch --version` under the expected architecture
  runner or emulator;
- SBOM and provenance refer to the exact commit and artifacts; and
- a failed platform build publishes no partial GitHub Release.

### Slice 7: add bounded upstream compatibility monitoring

Predecessor: Slice 4; it may be delivered independently of release automation.

Add a weekly and manually dispatchable workflow that tests only small,
documented compatibility surfaces:

- current-version/release discovery endpoints;
- `HEAD` or `Range: bytes=0-0` for pinned large artifacts where supported;
- response status, redirect, content length/range, and content-type invariants;
- selected lightweight metadata files; and
- known intentional authentication failures such as HMDB browser authorization.

The workflow must use bounded attempts, `Retry-After`, per-provider timeout,
and no CephFS credentials. It must not download KEGG entry collections, dbCAN
bundles, InterProScan archives, HMDB databases, or other large payloads.

Failures create an inspectable workflow artifact with endpoint, status,
attempts, and timestamp. Repeated verified behavior belongs in
`docs/compatibility/`; transient output does not.

Acceptance:

- a manual smoke run completes within 10 minutes;
- total downloaded bytes stay under a documented small budget;
- provider failures are isolated and diagnosable; and
- no secrets or licensed content appear in logs/artifacts.

## Intended review splits

Use short-lived PRs so compatibility, GitHub control-plane changes, and release
automation remain independently reviewable:

1. `feat(manifest): publish aggregate manifest v2` — existing local work only.
2. `docs(repo): converge publication and resource authority` — status,
   migration, license decision record, upstream terms, and citation scaffolding.
3. `refactor(module): adopt canonical github module path` — module/import/build
   changes plus installation verification.
4. `ci(repo): strengthen validation and security gates` — tests, pinned tools,
   Dependabot, templates, and stable required check.
5. `ci(release): build attested versioned artifacts` — release workflow and dry
   run evidence.
6. `ci(upstream): monitor bounded source compatibility` — scheduled live smoke.
7. `chore(release): publish v0.1.0` — changelog, tag, release, and readback.

Do not arm a new required check, mutate security settings, or publish a tag in
the same unverified external write. Each control-plane mutation requires a
successful check/readback first.

## Risks and mitigations

### Legal ambiguity

The repository downloads third-party databases with heterogeneous terms.
Mitigate by separating code licensing from upstream-data terms, linking official
terms, and avoiding data redistribution. Static release binaries also carry
third-party Go dependency obligations: generate and review
`THIRD_PARTY_NOTICES` from the exact release graph, and fail publication on an
unknown or unreviewed reciprocal license. Apache-2.0 applies only to
repository-owned code and documentation. This plan is engineering guidance,
not legal advice.

### Module-path breakage

The import rewrite is broad but mechanically bounded. All implementation
packages are internal. Run the complete test/race/build gates and the real
remote `go install` acceptance before release.

### Required-check lockout

Changing workflow/job names can make the active ruleset permanently wait for a
nonexistent context. Keep `validate-biofetch` stable; add and observe new checks
before updating any ruleset.

### Release publishes partial or wrong artifacts

Build and verify all platform artifacts before creating the GitHub Release.
Use immutable checksums, provenance, and tag-to-main validation. Never move a
published tag to repair metadata.

### Upstream smoke causes load or access violations

Use small documented endpoints, strict byte/time budgets, low frequency, and
provider-specific exclusions. Do not turn scheduled smoke into a hidden bulk
downloader.

### Public docs expose internal infrastructure

Use generic example paths in README and public how-to guides. Keep concrete
CephFS measurements only as clearly labeled benchmark evidence and never make
internal paths, AO, or node-specific state prerequisites for public use.

## Rollback and recovery

- Repository documents and templates can be reverted without affecting raw
  snapshots.
- The module-path change may be reverted before the first tag. After a public
  tag, do not reuse or move it; publish a corrective patch version.
- New CI checks remain non-required until they have succeeded on the exact
  intended branch. If a required-check mutation is wrong, restore the previous
  known check context through the GitHub ruleset API and read it back.
- A failed release workflow must leave no partial public Release. If an external
  write has unknown outcome, read back the tag/release before retrying.
- Security-setting changes are external control-plane mutations; record and
  verify each one independently.
- None of these changes mutates CephFS snapshots. Resource publication and
  aggregate publication retain their separate authorization and rollback
  contracts.
